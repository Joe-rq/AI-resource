实际工作场景与最佳实践

以下是社区和官方文档中验证过的、效果较好的工作流使用场景。每个场景都标注了推荐的触发方式和预期效果。

🚀 标杆案例：Bun 从 Zig 迁移到 Rust

真实案例数据

Jarred Sumner 使用动态工作流将 Bun 从 Zig 移植到 Rust：

  • 约 750,000 行 Rust 代码生成
  • 99.8% 测试套件通过
  • 从首次提交到合并仅 11 天
  • 数百个代理并行工作

该案例使用了四个工作流阶段：生命周期映射 → 逐文件移植（双评审员） → 构建修复循环 → 夜间优化提 PR。

效果出色的场景推荐

🔍

代码库范围安全审计

推荐：ultracode: / /deep-research

扫描整个代码库查找安全漏洞：硬编码密钥、不安全反序列化、废弃 API 调用、缺失的认证检查。

最佳实践：先只读扫描确认问题，再分组按严重程度处理。让独立代理验证每个发现。
🏗️

大规模代码迁移

推荐：ultracode: / /effort ultracode

框架升级、语言移植（如 Zig → Rust）、数据库迁移、API 版本升级。涉及数百文件的一致逻辑变更。

最佳实践：先在子目录上试运行，确认模式后再全量执行。要求 Claude 为每个变更生成测试验证。
🧪

测试覆盖率生成

推荐：ultracode: / 保存的工作流

为现有代码生成有意义的测试。每个模块可独立处理，天然适合并行。

最佳实践：按模块拆分代理，每个代理负责一个目录。最后汇总覆盖率报告。
📊

技术尽职调查 / 深度研究

推荐：/deep-research

竞品分析、技术选型调研、文献综述。多角度扇出搜索，交叉验证来源，投票过滤不可信声明。

最佳实践：问题要足够复杂才值得用 /deep。简单问题直接用普通对话更快。
🔧

复杂重构规划

推荐：ultracode: 只读分析

分析膨胀的类/模块，提出拆分方案。多个代理分别从架构、测试影响、API 兼容性、回滚风险角度评审。

最佳实践：第一阶段只分析不修改，让多代理评审方案后再执行。类似真实的技术设计评审。
⚔️

多轮对抗性验证

推荐：ultracode: / 保存的工作流

第1组找问题 → 第2组验证证据 → 第3组尝试推翻结论 → 第4组给出修复建议。

适用：安全审计、线上事故复盘、性能瓶颈定位、重要 PR 风险检查、架构方案评审。
🧹

技术债务系统清理

推荐：/effort ultracode / 保存的工作流

清理遗留模式、未使用导入、废弃依赖、不一致的格式、重复代码。可按目录并行处理。

最佳实践：保存为工作流后可在每次迭代前定期运行，保持代码库整洁。
📋

PR 批量审查

推荐：保存的工作流 + gh CLI

自动审查 PR 中的 bug、安全问题、风格不一致。可批量处理多个 PR 或对一个大型 PR 分模块审查。

最佳实践：与 gh CLI 配合：gh pr diff 123 | claude -p "Review this PR..."
✅

深度验证（逐条溯源）

推荐：ultracode: / 保存的工作流

对每条事实都要标注出处的报告，由一个代理识别各项论断，子代理逐一详细核查，再由验证代理确保来源质量。

适用：技术白皮书审核、事故复盘报告、合规性文档、对外发布的技术博客。
🏆

排序与锦标赛筛选

推荐：ultracode: / 保存的工作流

定性衡量大型条目列表（如按缺陷严重程度给工单排序）。用锦标赛、成对比较或先并行分桶再合并，每次比较都是一个独立代理。

适用：工单优先级排序、简历筛选、命名竞赛、方案比选。避免 1000+ 行内容撑爆上下文。
🧠

记忆与规则遵循

推荐：ultracode: / 保存的工作流

当 Claude 即便把规则写进 CLAUDE.md 仍会漏掉规则时，创建带规则验证器的 workflow。也可反向挖掘：从近期会话中找出反复出现的纠正，聚类提炼为新规则。

模式：一条规则配一个验证器 + 怀疑者角色审查 → 对抗式验证 → 幸存规则写回 CLAUDE.md。
🎯

大规模分类处理（Triage）

推荐：保存的工作流 + /loop

对条目分类、与现有记录去重、然后采取行动。配合 /loop 可持续运行。一个实用模式是"隔离区"：读取不受信任内容的代理被禁止执行高权限操作。

适用：工单分类、用户反馈处理、漏洞分级、内容审核。配合 /loop 做持续值守。
🎨

探索与品味决策

推荐：ultracode: / 保存的工作流

设计或命名这类依赖品味的决策，能从评分标准中受益。让 Claude 探索解法，同时让一个评审代理依据 rubric 评判，满足标准时即告完成。

适用：CLI 工具命名、UI 组件设计、API 命名、Logo/品牌方案比选。用锦标赛模式选出最佳。
⚖️

评估与智能路由

推荐：保存的工作流 / ultracode:

跑轻量级 eval：在 worktree 里生成独立 agent，再生成 comparison agent 对照 rubric 打分。也可创建 classifier agent 根据任务复杂度自动路由到 Sonnet 或 Opus。

适用：技能质量评估、模型选型、任务复杂度预估。大量工具调用时智能路由最有价值。

⚠️ 不适合使用工作流的场景

这些情况用普通对话更好
  • 单文件修改：写函数、修 bug、解释代码片段 → 用标准对话更快
  • 交互式开发：结对编程、需求探索、原型迭代 → 工作流延迟太高
  • 紧密耦合的变更：模块间依赖极强，并行反而增加协调成本 → 用大上下文窗口顺序处理
  • 成本敏感的小任务：token 消耗是单代理的 10-100 倍 → 确认值得再投入
  • 需要中途人工介入：工作流运行中无法输入，只能暂停或停止
  • 常规编码任务：大多数传统编码并不需要五个 reviewer → 掂量一下是否真的需要额外算力

💡 最佳实践总结

  1. 先小范围试运行：一个目录而不是整个仓库，评估 token 消耗和效果后再扩大
  2. 给足上下文：与其说"修复认证模块"，不如说"认证模块有三个已知问题：[列表]。下季度还要加 OAuth，请一并考虑"
  3. 分离思考与执行：先用工作流做分析和规划，审查方案后再启动执行工作流
  4. 保持干净的 git 状态：每次工作流前提交当前代码，方便审查完整 diff
  5. 定期保存工作流：完成的工作流按 s 保存，变成可复用的团队资产
  6. 搭配 Auto 权限模式：长时间无人值守运行时开启，避免每次批准中断

工作流简介

动态工作流是一个 JavaScript 脚本，可大规模编排子代理。Claude 为您描述的任务编写脚本，运行时在后台执行它，同时您的会话保持响应。

版本要求

动态工作流处于研究预览阶段。它们需要 Claude Code v2.1.154 或更高版本，在所有付费计划上可用。在 Pro 上，从 /config 中的"Dynamic workflows"行启用它们。

何时使用工作流：

  • 代码库范围的错误扫描
  • 500+ 文件的大型迁移
  • 需要相互交叉检查来源的研究问题
  • 在提交前需要从多个独立角度起草的困难计划

为什么需要工作流：三种失效模式

默认的 Claude Code 在单个上下文窗口内完成规划与执行，这对编码任务很有效，但面对长时间运行、大规模并行或带对抗性质的任务会出现三种失效模式：

01

智能体偷懒

面对复杂的多部分任务，Claude 会过早停止。比如 50 项安全审查只处理了 35 项就宣布完成。

02

自我偏好偏差

当被要求对照评分标准验证或评判结果时，Claude 会偏袒自己得出的结论，缺乏客观性。

03

目标漂移

在多轮交互中保真度逐渐流失，每一次总结都会丢掉细节，包括边缘情况和各种约束。

工作流的对策：编排一批彼此独立、各自拥有独立上下文窗口、目标聚焦又互相隔离的子代理。每个代理只负责一小块任务，结果汇总到脚本变量中，避免了上述三种失效。

P

6 种可复用模式

触发工作流后，Claude 会根据任务自动选择或组合以下模式。你也可以在提示中明确要求使用某种模式。

01

分类并执行 Classify & Execute

由一个分类器代理判断任务类型，据此路由到不同的代理或行为。也可以在任务完成时确定输出的分类。

示例： incoming bug 报告 → 分类为"前端/UI"、"后端/API"、"基础设施" → 分别路由给对应领域的专家代理处理。
02

扇出并综合 Fan-out & Synthesize

把任务拆成许多更小的步骤，每个步骤跑一个代理，再综合所有结果。综合这一步充当一个屏障，它会等所有扇出的代理完成后，再合并它们的结构化输出。

示例：代码库审计 → 50 个代理各负责一个目录 → 屏障等全部完成后 → 汇总为一份统一报告。
03

对抗式验证 Adversarial Verification

每生成一个代理，就再跑一个单独的代理以对抗的姿态对照 rubric 或判定准则来验证它的输出。这是对抗性偏差最直接的解药。

示例：代理 A 得出结论"此函数存在 SQL 注入" → 验证代理 B 必须找到证据推翻或确认该结论 → 只有通过交叉检查的才保留。
04

生成并筛选 Generate & Filter

先就某个主题生成多个想法，再按 rubric 或验证来筛选，去重后只留下质量最高、经过检验的那些。

示例：为 CLI 工具生成 20 个候选名称 → 按 rubric（简洁、可发音、无歧义、域名可用）筛选 → 去重 → 保留 Top 5。
05

锦标赛 Tournament

让 N 个代理用不同方法在同一个任务上互相竞争，而不是把工作分摊下去。由成对评判的代理决出胜者，直到只剩一个。

示例：3 个代理用不同算法解决同一优化问题 → 评判代理两两比较 → 胜者进入下一轮 → 最终选出最优方案。
06

循环至完成 Loop to Completion

对工作量未知的任务，持续生成代理，直到满足停止条件为止（比如不再有新发现、日志里不再有错误），而不是采用固定的遍数。

示例：持续扫描构建日志修复错误 → 每轮修复后重新构建 → 直到构建成功且测试全过 → 自动停止。

模式组合

实际工作流中，这些模式经常组合使用。比如"扇出并综合"+"对抗式验证"是审计和研究类任务的经典组合；"生成并筛选"+"锦标赛"是设计决策的强力搭配。你可以在提示中要求 Claude 采用特定模式。

子代理、skills、agent teams 和工作流都可以运行多步骤任务。区别在于谁掌握计划：

特性 子代理 Skills Agent Teams 工作流

工作流将计划移入代码。脚本持有循环、分支和中间结果本身，所以 Claude 的上下文只持有最终答案。这也让工作流可以应用可重复的质量模式：让独立代理在报告之前对彼此的发现进行对抗性审查，或从多个角度起草计划并相互权衡。

运行捆绑工作流

查看工作流运行的最快方式是运行 /deep-research，这是 Claude Code 包含的内置工作流，用于跨许多来源调查问题。

运行工作流

使用您想要调查的问题运行 /deep-research。它在多个角度上扇出网络搜索，获取并交叉检查来源，并综合一份引用的报告。

输入 
/deep-research What changed in the Node.js permission model between v20 and v22?
允许工作流

Claude Code 询问是否允许工作流。选择是继续。确切的提示取决于您的权限模式。

观看进度

运行在后台启动。运行 /workflows，使用箭头键选择运行，然后按 Enter 打开其进度视图：

输入 
/workflows

该视图显示每个阶段及其代理计数、令牌总数和经过的时间。深入任何阶段以查看其代理及每个代理发现的内容。

阅读报告

运行完成后，报告进入您的会话。它引用每个声明来自的来源，未通过交叉检查的声明已被过滤掉。

捆绑工作流

命令 功能
/deep-research <question> 在多个角度上扇出网络搜索问题，获取并交叉检查来源，对每个声明投票，并返回一份引用的报告。需要 WebSearch 工具可用。

您自己保存的工作流以相同方式成为命令，并在 / 自动完成中与捆绑的工作流一起出现。

Enter 或 → 深入选定的阶段，然后进入代理以读取其提示、最近的工具调用和结果
Esc 返回一个级别
j / k 当代理详情溢出时在其中滚动
p 暂停或恢复运行
x 停止选定的代理，或当焦点在运行上时停止整个工作流
r 重启选定的运行中代理
s 保存运行的脚本作为命令
5

让 Claude 编写工作流

您可以通过以下两种方式让 Claude 为您的任务编写工作流：

📝

提示中请求

在提示中包含关键字 ultracode，Claude 为单个任务编写工作流

⚡

Ultracode 模式

设置 /effort ultracode，Claude 为每个实质性任务自动规划工作流

6

在提示中请求工作流

要在不改变会话的努力级别的情况下将单个任务作为工作流运行，在您的提示中包含关键字 ultracode。用您自己的话提问（如"使用工作流"或"运行工作流"）也可以工作。

示例 
ultracode: audit every API endpoint under src/routes/ for missing auth checks

提示

Claude Code 会在您的输入中高亮该关键字。如果不打算启动工作流，在 macOS 上按 Option+W 或在 Windows/Linux 上按 Alt+W 来忽略高亮。要完全停止关键字触发，请在 /config 中关闭 Ultracode 关键字触发。

7

Ultracode 模式

Ultracode 是一个 Claude Code 设置，它结合了 xhigh 推理努力与自动工作流编排。启用后，Claude 为每个实质性任务规划工作流，而不是等待您要求。

启用命令 
/effort ultracode

启用后，Claude 决定任务何时值得工作流。单个请求可以变成一系列工作流：一个理解代码，一个进行更改，一个验证它。适用于会话中的每个任务，但会使用更多令牌并花费更长时间。

⚠️ 注意

Ultracode 持续当前会话，启动新会话时重置。当您返回日常工作时，使用 /effort high 下降。它在支持 xhigh 努力的模型上可用。

8

在运行前批准计划

在 CLI 中，每次运行的提示显示计划的阶段和以下选项：

  • 是，运行它：启动运行
  • 是，不再询问：启动，并跳过此项目中此工作流的后续提示
  • 查看原始脚本：在决定前读取脚本
  • 否：取消

Ctrl+G 在您的编辑器中打开脚本。Tab 让您在运行启动前调整提示。

权限模式与提示行为

权限模式 何时提示
默认，接受编辑 每次运行，除非已为此项目中的该工作流选择"是，不再询问"
自动 仅首次启动。任何"是"在用户设置中记录同意，之后无需提示。Ultracode 启用时完全跳过
绕过权限，claude -p，Agent SDK 从不。运行立即启动

工作流生成的子代理始终在 acceptEdits 模式下运行，并继承您的工具允许列表。文件编辑自动批准，但 Shell 命令和网络获取仍可能提示您。

9

保存工作流以供重用

当 Claude 为您编写了好用的工作流时，您可以将该运行的脚本保存为命令，以便重复运行相同的编排。

选择运行

运行 /workflows，选择您想保留的运行，然后按 s。

选择保存位置

按 Tab 在两个保存位置之间切换：

  • .claude/workflows/ 在项目中：与团队共享，克隆仓库的每个人都可用
  • ~/.claude/workflows/ 在主目录中：仅对您可见，在每个项目中可用
保存并使用

按 Enter 保存。工作流在未来会话中从任一位置作为 /<name> 运行。如果项目工作流和个人工作流共享名称，项目工作流优先运行。

💡 构建工作流的进阶技巧

结合 /goal 和 /loop

对可重复的工作流（如分类、研究、验证），用 /loop 按固定间隔运行，用 /goal 设一个硬性的完成要求。这样工作流会持续运行直到目标达成。

示例 
/goal 修复所有构建错误
/loop 每 5 分钟运行一次修复工作流，直到构建成功

设置 Token 预算

在提示中写明上限，让 Claude 在预算内完成任务。这对控制成本非常有效。

示例 
ultracode: 审计 src/ 目录下的认证问题，token 预算 10000，超出时暂停并报告

通过 Skills 分发工作流

把 JavaScript 工作流文件放进技能文件夹，并在 SKILL.md 里引用。这样团队成员安装技能后即可使用。也可以提示 Claude 把技能里的工作流当成模板，而不是逐字照搬的脚本。

提示词要写详细

运用上面讲的那些具体技巧、把提示写详细，效果最好。工作流不只用于大型任务，你也可以提示一个快速工作流，比如对某个假设做一次快速的对抗式审查。

10

将输入传递给保存的工作流

保存的工作流可以通过 args 参数接受输入。脚本将其读取为名为 args 的全局变量。使用此功能在调用时提供研究问题、目标路径列表或配置对象，而不是为每次运行编辑脚本。

示例 
> Run /triage-issues on issues 1024, 1025, and 1030

Claude 将列表作为结构化数据传递，所以脚本可以直接在 args 上调用数组和对象方法，无需先解析。如果省略 args，脚本内的全局变量为 undefined。

11

工作流如何运行

工作流运行时在隔离环境中执行脚本，与您的对话分开。中间结果保留在脚本变量中，而不是进入 Claude 的上下文。

  • 每次运行将其脚本写入会话目录下 ~/.claude/projects/ 中的文件
  • 运行开始时 Claude 会收到该路径，您可以要求它提供
  • 您可以打开该文件来读取编排脚本，与之前运行对比，或编辑它并从编辑后的版本重新启动
  • 运行时跟踪每个代理的结果，使运行在同一会话中可恢复
12

行为与限制

约束 原因
无中途用户输入 仅代理权限提示可以暂停运行。阶段之间的签署，将每个阶段作为其自己的工作流运行
无来自工作流本身的直接文件系统或 shell 访问 代理读取、写入和运行命令。脚本协调代理
最多 16 个并发代理（CPU 核心有限的机器上更少） 限制本地资源使用
每次运行 1,000 个代理总数 防止失控循环
13

管理运行

运行启动后，您可以从 /workflows 视图管理它，或通过展开输入框下方任务面板中的其进度行来管理。

14

暂停后恢复

如果您停止运行，您可以恢复它：已完成的代理返回其缓存结果，其余的实时运行。恢复方式：

  • 从 /workflows 恢复暂停的运行，选择它并按 p
  • 或要求 Claude 使用相同脚本重新启动工作流
⚠️ 注意

恢复在同一 Claude Code 会话中工作。如果您在工作流运行时退出 Claude Code，下一个会话将从头启动工作流。

15

成本控制

工作流生成许多代理，单次运行可以使用比在对话中处理相同任务更多的令牌。运行计入您的计划使用和速率限制。

成本优化建议

  • 在提交大型任务前，先在小范围上运行工作流：一个目录而不是整个仓库，或一个狭窄的问题而不是宽泛的问题
  • /workflows 视图显示每个代理的令牌使用情况，您可以随时停止运行而不会丢失已完成的工作
  • 在大型运行前检查 /model，如果您通常为日常工作切换到较小的模型
  • 描述任务时，要求 Claude 为不需要最强模型的阶段使用较小的模型
  • 每次运行 1,000 个代理的上限限制了失控脚本的成本
16

关闭工作流

工作流在 CLI、桌面应用、IDE 扩展、非交互模式与 claude -p 和 Agent SDK 中可用。相同的禁用设置在每个表面上应用。

为自己关闭

方法 效果
/config 中切换 "Dynamic workflows" 关闭 在会话中持续
~/.claude/settings.json 中设置 "disableWorkflows": true 在会话中持续
设置环境变量 CLAUDE_CODE_DISABLE_WORKFLOWS=1 在启动时读取，在任何设置的地方应用

为整个组织关闭

在托管设置中设置 "disableWorkflows": true，或使用 Claude Code 管理员设置页面上的切换。

关闭后的效果

当工作流被禁用时，捆绑工作流命令不可用，ultracode 关键字不再触发运行，ultracode 从 /effort 菜单中移除。
