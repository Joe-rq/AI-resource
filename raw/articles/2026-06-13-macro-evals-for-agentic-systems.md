# 智能体系统宏观评估教程

这份教程改写自原文的 OpenAI Cookbook 案例，主题是：当一个多智能体系统出问题时，不只看某一次回答错在哪里，而是把很多次运行轨迹放在一起，找出反复出现的系统性行为模式。

案例背景是一个电动车订单处理系统。用户配置好车辆后，系统需要判断订单能否直接放行、是否需要改配置、是否要换供应商、是否要重新排产、是否涉及价格或合规风险，以及是否需要人工复核。这个系统由多个专家智能体协作完成，例如定价、合规、供应、工厂路由、排期、客户沟通和最终放行审查。

## 1. 为什么要做宏观评估

普通评估通常只回答一个问题：这一次输出是否正确。

智能体系统需要回答更多问题：

- 是否调用了正确工具；
- 是否交给了正确专家智能体；
- 是否在高风险场景里触发了复核；
- 是否正确使用了供应、价格、政策、市场等上下文；
- 是否在很多运行中反复出现同一类错误。

所以评估要拆成两层：

- 底层评估：看单次运行里的局部问题，例如某个智能体是否判断正确、交接是否合理、工具调用是否充分。
- 宏观评估：把很多底层评估结果聚合起来，找出重复出现的行为模式，并判断优先排查哪里。

一个好用的心智模型是：

- `case_type`：这次运行的业务场景是什么。
- `run_outcome`：这次运行最后怎么结束。
- `eval_finding`：底层评估发现了什么局部风险。
- `behavior_pattern`：很多运行聚合后发现的重复行为模式。

也就是说：

```text
case_type -> run_outcome -> eval_finding -> behavior_pattern
业务场景 -> 运行结局 -> 局部症状 -> 群体模式
```

## 2. 准备数据

宏观评估依赖的不是普通聊天记录，而是完整的智能体运行证据。原文案例使用了离线数据，因此不需要实时调用 OpenAI API。

需要准备的数据包括：

- `trace_results.jsonl`：每次运行的结果摘要。
- `run_summary.json`：整批运行的整体摘要。
- `trace_bundles.zip` 或 `trace_bundles/`：每次运行的完整证据包。
- `eval_labels.jsonl`：底层评估标签，例如 Promptfoo 生成的评分结果。
- `trace_snapshot.sqlite`：可选，用于补充更完整的 trace 快照。

如果数据不在默认目录，可以用环境变量指定：

- `MACRO_EVALS_DATA_ROOT`：数据根目录。
- `MACRO_EVALS_LABELS_PATH`：底层评估标签文件路径。
- `MACRO_EVALS_TRACE_LIMIT`：限制分析多少条 trace，适合本地调试。
- `MACRO_EVALS_DISCOVERY_MIN_CLUSTER_SIZE`：聚类时的最小簇大小，控制一个模式至少需要多少条运行支持。

其中 `MACRO_EVALS_DISCOVERY_MIN_CLUSTER_SIZE` 是影响模式发现粒度的超参数。它越大，得到的模式越粗、更稳定；它越小，越容易发现小众模式，但也更容易出现噪声。

## 3. 理解单次运行证据包

每个 `bundle` 可以理解为一次客户订单交互的审计包。它记录了系统看到什么、做了什么、交给了谁、调用了哪些工具，以及最后为什么得出某个结果。

一个典型 `bundle` 包含：

- `run`：运行编号、trace 编号、终态、批次信息和订单上下文。
- `events`：标准化事件流，包括状态变化、交接、工具调用、模型响应和发现的问题。
- `spans`：更底层的 SDK trace 片段，用于还原模型调用、工具调用和交接结构。
- `environment_events`：本次订单面对的外部环境，例如关税、促销、缺货、竞品压力、产能或排期变化。
- `review_packet`：复核记录，包括发现的问题、建议动作、允许动作和复核状态。
- `snapshots`：可选的库存、产能和环境快照。

宏观评估需要这些证据，因为最终答案可能看起来合理，但 trace 里可能暴露出系统绕过了定价检查、忽略了缺货信号，或者过早跳过人工复核。

## 4. 建立业务场景覆盖

先不要急着聚类。第一步是看模拟数据是否覆盖了足够多的业务压力。

原文案例中的 `case_type` 包括：

- `clean_simple`：简单订单，通常应该快速完成，不应产生不必要复核。
- `validation_block_simple`：配置存在验证问题，系统不能自信放行。
- `supplier_substitution_compound`：供应商或部件可用性导致替换决策。
- `pricing_exception_compound`：价格、激励、利润或关税压力需要定价专家介入。
- `regional_compliance_compound`：区域政策或合规约束影响订单释放。
- `clarification_needed_compound`：客户意图或配置细节不清楚。
- `schedule_incentive_compound`：排期和激励窗口相互影响。
- `conflicting_multi_agent_compound`：多个专家智能体可能给出冲突建议。

这一步的目标是回答：

- 普通场景和压力场景是否都有；
- 每类场景数量是否足够；
- 后续发现的行为模式是否可能只是某类场景样本过少导致的偶然现象。

## 5. 做底层智能体评估

底层评估负责给每次运行打局部标签。原文使用 Promptfoo 表示这一层。

评估问题包括：

- 最终决策是否符合当前业务问题；
- 是否正确处理价格、关税、激励、区域和政策约束；
- 编排器是否激活了场景需要的专家；
- 系统是否注意到有时间属性的市场变化；
- 复核或升级是否与风险程度匹配。

这些评估会生成 `eval_finding`。它不是宏观结论，而是单次运行里的局部症状。例如：

- `final_decision_quality`：最终决策质量有问题。
- `policy_compliance_correctness`：政策或合规处理有问题。
- `routing_specialist_activation`：专家路由不合理。
- `market_drift_awareness`：没有正确响应市场变化。
- `review_appropriateness`：复核触发过早、过晚或不必要。

底层评估的价值是提供信号；宏观评估的价值是判断这些信号是否组成了系统性模式。

## 6. 构建分析数据集

把原始 `bundle` 标准化成两张核心表：

- `traces_df`：一行代表一次运行，包含业务元数据、最终状态、底层发现、严重度和用于聚类的文档字段。
- `events_df`：一行代表一个标准化事件，包含交接、工具调用、状态事件、模型响应和复核标记。

然后基于 `traces_df` 和 `events_df` 构建 trace document。

`doc_structured_summary` 是每条 trace 的压缩叙事版本。它不是给人看的完整报告，而是给聚类算法看的建模对象。它应该保留：

- 业务场景；
- 运行结局；
- 激活过的专家；
- 关键交接；
- 外部环境信号；
- 复核或失败标记；
- 简短状态转移摘要。

这里的关键设计点是：聚类算法只能发现文档里保留下来的信息。如果文档里没有交接信息，就很难发现路由模式；如果没有环境信号，就很难发现市场变化相关问题。

## 7. 给每次运行计算严重度和影响分

原文把运行结局映射成严重度：

- `completed`：成功完成，低严重度。
- `awaiting_review`：等待复核，中等严重度。
- `blocked` 或 `failed`：阻塞或失败，高严重度。

`impact_score` 用于衡量某条 trace 的排查优先级。它综合了：

- 运行结局的严重度；
- 发现的问题数量；
- 是否存在循环、重试或复杂路径。

这个分数的作用不是证明风险大小，而是帮助团队把注意力优先放到更可能有业务影响的运行上。

## 8. 先看聚类前的业务流

在发现行为模式之前，可以先画一张流向图：

```text
case_type -> run_outcome -> eval_finding
```

它可以回答：

- 哪些业务场景最常出现；
- 哪些场景更容易完成、复核、阻塞或失败；
- 哪些底层评估发现最集中。

但它还不能回答：这些局部发现是不是同一种底层行为模式。比如很多 trace 都有 `final_decision_quality` 问题，但原因可能分别是价格信号没用、供应商替换没处理、合规门槛绕过、复核阈值不合理。下一步才是宏观发现。

## 9. 用 BERTopic 风格方法发现行为模式

原文使用 BERTopic 风格的流程，不一定要求完全使用 BERTopic 包，但思想一致：

1. 把每条 trace document 转成向量。
2. 用 UMAP 这类方法降低维度，让相似 trace 更容易靠近。
3. 用 HDBSCAN 这类密度聚类方法找出高密度簇，并允许把噪声标成离群点。
4. 给每个簇提取有区分度的关键词。
5. 把每个簇解释成一个 `behavior_pattern`。

`behavior_pattern` 是宏观评估的核心输出。它不是某一次运行的错误，而是很多运行共同表现出来的模式，例如：

- 供应或履约路由反复绕行；
- 定价或市场信号处理漂移；
- 合规门槛集中触发；
- 轮毂、内饰、配置等选项不匹配；
- 干净订单中出现不必要升级。

模式发现后，要按影响排序。原文的模式级排序思路是：

```text
pattern impact = prevalence x severity_weighted_prevalence
```

其中：

- `prevalence` 表示这个模式有多常见。
- `severity_weighted_prevalence` 表示这个模式里的运行平均有多严重。
- `impact_score` 表示它作为排查对象的优先级。

高影响模式不等于一定是缺陷。它的意思是：这个模式又常见又可能有后果，值得优先让人看。

## 10. 按业务切片理解模式集中在哪里

发现 `behavior_pattern` 之后，要把它和业务切片连接起来。

常见切片包括：

- `case_type`：业务场景。
- `agent_version_set`：智能体版本组合。
- `orchestrator_mode`：编排器模式。
- `market_regime`：市场环境。
- `price_regime`：价格环境。
- `schedule_regime`：排期环境。
- `review_status`：复核状态。

这里可以使用 `lift` 判断某个模式是否在某个切片里异常集中：

```text
lift = slice_pattern_share / overall_pattern_share
```

含义是：

- `overall_pattern_share`：这个模式在全部聚类 trace 里的占比。
- `slice_pattern_share`：这个模式在某个业务切片里的占比。
- `lift > 1`：模式在该切片里更集中。
- `lift = 1`：模式在该切片里的出现频率和整体差不多。
- `lift < 1`：模式在该切片里不突出。

这一步能把“发现了一个模式”变成“它主要出现在什么业务条件下”。

例如，一个履约路由模式如果集中在 `supplier_substitution_compound`，优先检查供应商替换工具、采购交接和履约策略。如果它集中在 `clean_simple`，那更可能是系统对简单订单过度复杂化。

## 11. 聚类后再看完整业务流

聚类后再画一次流向：

```text
case_type -> run_outcome -> eval_finding -> behavior_pattern
```

这张图是宏观评估的共享地图。

业务方可以用它问：

- 哪些订单场景正在产生最多重复问题；
- 这些问题是否真的对应重要业务结果；
- 是否需要调整流程、政策或复核阈值。

工程方可以用它问：

- 哪些局部评估失败其实是同一种路由问题；
- 哪些行为模式和特定智能体版本有关；
- 哪些模式应该加入回归测试。

## 12. 用 AgentTrace 风格方法做根因诊断

发现模式之后，还需要知道优先排查哪里。

原文使用 AgentTrace 风格诊断：为某个高影响 `behavior_pattern` 重建轻量执行图。

执行图可以理解为：

```text
G = (V, E)
```

- `V` 是事件节点，例如状态变化、工具调用、交接、模型响应、复核标记。
- `E` 是事件之间的关系，例如时间顺序、交接关系、工具调用上下文。

然后选择一个 `focus_event`，也就是诊断锚点。常见锚点包括：

- 复核发现；
- 等待复核；
- 阻塞或失败状态；
- 路由变化；
- 工具警告或政策标记。

从 `focus_event` 往前回溯，给上游嫌疑节点打分。原文的 `suspect_score` 综合了：

- `proximity`：离锚点越近，越值得看。
- `frequency`：在同一模式的多条 trace 中越常出现，越值得看。
- `bridge`：是否连接了执行图里的关键路径。
- `role`：这个节点的智能体或工具角色是否和问题相关。

这不是因果证明，而是排查排序。它把“这个模式很重要”推进到“先查哪些智能体、工具、交接或复核策略”。

## 13. 怎么读诊断结果

诊断结果通常会给出 suspect leaderboard，也就是嫌疑节点排行榜。

如果榜首是 `eval/review signal`，它通常只是问题被发现的位置，不一定是根因。真正更可操作的是周围的业务事件，例如：

- 编排器是否把订单交给了正确专家；
- 某个工具是否输出了风险信号但后续没有使用；
- 某次 handoff 是否发生得太早或太晚；
- 某个专家智能体的响应是否误导了后续决策；
- 复核标记是否触发时机不合理。

可以配合两类图阅读：

- story strip：展示进入锚点前的一条代表性路径。
- swimlane：按智能体或执行 lane 展示锚点前后的时间窗口。

阅读顺序是：

1. 先看模式是什么；
2. 再看锚点是什么；
3. 找到第一个非复核类的 operational suspect；
4. 回到代表 trace，检查它之前的交接、工具输出和智能体响应；
5. 判断应该修提示词、工具协议、交接规则、复核阈值，还是业务政策本身。

## 14. 把结果转成行动

对 AI 工程团队，下一步通常是：

- 把最清晰的底层评估失败加入回归测试；
- 抽样复核自动评分，校准 Promptfoo 或其他评估器的严格程度；
- 按模型版本、提示词版本、编排模式持续跟踪 `behavior_pattern`；
- 优先检查高影响模式里的智能体说明、工具 schema、handoff 规则和复核逻辑；
- 对映射或路由类错误，把代表性失败样例纳入验证集。

对业务团队，下一步通常是：

- 判断模拟的 `case_type` 是否覆盖真实运营风险；
- 检查高影响模式是否对应真实客户影响或运营成本；
- 校准人工复核阈值是否过严或过松；
- 用热力图和 Sankey 流向图决定哪些业务场景最需要流程或政策调整。

## 15. 迁移到自己项目时的最小落地清单

如果要把这个方法迁移到自己的智能体系统，可以按下面顺序做：

1. 定义业务场景标签 `case_type`，先覆盖普通场景和高风险场景。
2. 确保每次运行都保存完整 trace，包括模型响应、工具调用、handoff、复核标记和外部环境信号。
3. 为单次运行建立底层评估，至少覆盖决策质量、政策正确性、路由合理性、环境感知和复核适当性。
4. 把原始 trace 标准化成 `traces_df` 和 `events_df`。
5. 构建 `doc_structured_summary`，让每条运行变成可比较的短文档。
6. 对失败、复核、阻塞或底层评估失败的 trace 做聚类。
7. 把聚类结果解释成 `behavior_pattern`，并按影响排序。
8. 用切片和 `lift` 判断模式集中在哪些业务条件、版本或编排模式里。
9. 对最高影响模式做 AgentTrace 风格回溯，找出优先排查的智能体、工具或交接。
10. 把已确认的问题样例加入验证集或回归集，避免后续改动让同类问题复发。

## 16. 核心结论

底层评估告诉你：某次运行哪里看起来有风险。

宏观评估告诉你：这些风险在系统规模上会变成什么重复模式。

真正的价值不在于给每条 trace 做完美分类，而在于把成百上千个智能体事件压缩成少数高影响、可解释、可分配责任的模式，让工程团队和业务团队能围绕同一张图讨论下一步该查什么、改什么、验证什么。
