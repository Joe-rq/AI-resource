## 3 起源故事：FDE 为什么被发明

**主持人**：先讲讲 OpenAI 现场部署工程团队的起源故事吧。为什么会成立这个团队？

**Colin**：好。ChatGPT 刚出来的时候，外界非常兴奋，但说实话**当时要从模型里挖出真实价值，是非常难的**。Copywriting 可能是当时唯一算得上"开箱即用"的场景。

**Colin**：我们在 ChatGPT 之后那几年发现了一件事：要把企业客户带到生产环境，过程**非常不一致**，每次都要花大量时间。但**唯一能持续成功**的共同点是——**驻场交付**：真正沉到客户的业务里，深刻理解他们的领域，坐在用户旁边，帮他们把技术用起来。

**Colin**：我们之前那种"远程技术支持"模式，**没办法可靠地把客户带到生产**。这才促使我们决定成立 FDE 团队——**用一套可重复的方法，把企业一次次带到生产**。

**主持人**：说得通。那 FDE 到底是做什么的呢？

## 4 摩根士丹利案例：把 RAG 做成"信任"

**Colin**：我想用具体案例来回答。我们最早想做 FDE 实践的契机之一是**摩根士丹利**——我们 2023 年为他们部署，他们也是我们**第一个在 GPT-4 上跑起来的企业客户**。

**主持人**：他们的场景是什么？

**Colin**：他们想把**财富管理**业务 AI 化。我得强调一点：**成功部署 GenAI 的人有个共同特点——他们不会选个边缘场景试试，他们挑的就是公司里高赌注的核心业务**。摩根士丹利的财富管理就是他们最大的业务板块之一。

**Colin**：我们要解决两件事：
1. 把他们的研究报告放到所有财富顾问手边，让他们能给出更可执行的洞察；
2. **让顾问信任这些输出**。

**Colin**：那时候 RAG 还不是个成型的概念。我们的做法是：

- **先做检索调优**，把模型输出的研究内容调到我们可以信任的程度；
- **跑飞行员测试**，让财富顾问标注数据；
- **反复迭代**，直到顾问真正把洞察用到了客户对话里。

**主持人**：效果怎么样？

**Colin**：大概六到八周就把主要技术难题解决了。但**建立信任又花了额外四个月**——做飞行员、收评测、反复打磨。最终的成果是：

- **98% 的财富顾问采用了系统**；
- **研究报告的使用量提升了 3 倍**。

**主持人**：六到八周搭出技术，额外四个月建立信任。原始产品其实几周就跑通了吧？

**Colin**：**差不多六天**——管线、护栏、检索调优一气呵成。但企业里**"多好多算够好"**这个问题很有意思。摩根士丹利是高度受监管的环境，对准确性要求极高；可这又是个**概率性技术**——你必须既搭出合适的框架，又让用户信任它，还得给他们工具去验证自己不信的部分。

**主持人**：那是 2023 年的事。

**Colin**：对。

## 6 欧洲半导体公司案例：调试调查分诊 Agent

**主持人**：给我们举一两个真正"动了指标"、有实质回报的例子吧。

**Colin**：好。我们现在最大的项目之一是和一家**欧洲半导体公司**合作。延续摩根士丹利的逻辑——**你必须挑大问题**。这家客户跟我们说：看一遍我们整条价值链，挑最浪费的环节，用 AI 把它提效。具体做什么，由我们定。

**主持人**：你们怎么入手的？

**Colin**：我们**驻场了两周**，把他们的业务从头到尾摸了一遍。整条价值链上有设计流程、验证流程、芯片出货后的性能测量。我们最后聚焦在**验证环节**——这恰好是工程师最不喜欢做、但又必须花 **78% 时间**去做的部分：修 bug、维护与旧版本芯片的兼容性，诸如此类。

**主持人**：那你们具体做了什么？

**Colin**：我们沿着价值链交付了**10 个不同的 FDE 用例**，最终目标是**节省 50% 的工程师时间**。目前在最先跑通的两三个部门，已经做到了 **20%–30%**。

### 6.1 "早晨到岗"场景：从被动响应到主动修复

**Colin**：他们每天要在芯片上跑大量测试，只能批量排在夜间跑。**工程师早上到工位时，每个人桌上可能堆着几百个 bug**。他们一坐下来就要硬着头皮从零开始 debug。

**Colin**：我们的做法是：

1. **以 Codex 为底座**，针对他们的领域做定制；
2. 第一步：让模型接 bug，做完调查，**给工程师开工单**，说"这个大概是这个问题"；
3. 工程师对结果建立信任之后，让模型**直接去修，并提 PR**；
4. 这时我们发现：必须**给模型一个执行环境**，让它能跑自己的代码、做迭代。

**Colin**：我们最后沉淀出来的东西叫**"调试调查分诊 Agent"（Debug, Investigation and Triage Agent）**。它能**自动修复相当大比例的 bug**——工程师早上到工位时，大部分已经被处理掉了。

### 6.2 远期愿景与当前瓶颈

**Colin**：我们的愿景是——到明年年中，工程师早上来工位，**大部分 bug 已经被修完，最难的那批被清晰文档化**，他们能直接动手去做更有价值的事。以前光是消化这几千个 bug，就要花**四到六周**——他们一边要修 bug，一边要写新代码，"转椅式切换"，心力交瘁。

**Colin**：我们希望工程师的世界变成：**只写新代码，模型去消化所有支撑性的 bug 修复**。

## 7 模型与团队的边界：谁负责什么

**主持人**：这是个有意思的"模型 vs 你的团队"的话题。**模型和团队之间的分界线在哪里？**这条线会随时间移动吗？

**Colin**：好问题。理想情况下，你走进系统说："这些是工程师能用的工具，这是问题，自己去修。"——也许有一天会走到那一步。但我们现在发现，要先做的第一件事是：

**Colin**：**先 fork Codex，加一堆遥测**，让我们能搭出**非常细颗粒度的评测集**。我们会说："如果我是工程师去修这个 bug，我会按这条具体路径走：检查这些日志、判断有没有问题……"我们会和客户那边的专家一起，**把这条路径做成一个 5-step 左右的标注集**，然后从那里开始。

**Colin**：退一步讲——就算你真到了那个"AI 自主解决一切"的完美未来，你还是需要**某种检查它工作的机制**。所以我们搭了一套评测框架，名字叫**"评测驱动的开发"（Eval-Driven Development）**——**一段 LLM 写的代码，只有在配齐了验证正确性的评测之后，才算"写完"**。这就是我们的起点。

**Colin**：回到你的问题——如果模型变强，我们只要跑评测集、过线就行。**但实际工程里，FDE 还得围绕这套评测搭一大堆脚手架**：

- 哪些部分必须**确定性执行**；
- 哪些部分我们用**模拟器当工具**调用，直接拿结果。

**主持人**：所以是**两者混合**。

**Colin**：对。

## 8 FDE 是产品工程，不是咨询

**主持人**：那转到产品这边。外面有个很大的吐槽——"不好意思用那个词"——**FDE 就是披着工程师外衣的咨询顾问**。

**主持人**：你们真的在造产品吗？如果是，**可复用的产品**和**给单一客户做的定制工作**，这条线在哪里？

**Colin**：确实有可复用产品那条线。比如半导体这个项目，我们会判断：这些代码最终能不能回流到 Codex，让它更好地服务企业用例？这是产品方向的工作。

### 8.1 更好的故事：Klarna → Swarm → AgentKit

**Colin**：但我想讲个更好的例子，要回到**2023 年**——我们另一个客户是 **Klarna**。我跟他们合作了一阵子，做了不少东西。但我们交付给他们的第一样东西是**客服应用**。

**Colin**：客服场景里有个现实问题：很难规模化。如果每条策略你都**手工写 prompt**，而他们有 **400 条策略**——这显然不可扩展。所以我们搞了个方法：

1. **把指令和工具参数化**；
2. **给每个意图包一组评测**。

**Colin**：这样我们就能从 20 条策略**扩展到 400 条甚至更多**。这套方法在 Klarna 跑得不错。

**Colin**：之后我们决定——**把它产品化**。我们把它做成一个**开源框架**，内部叫 **Swarm**，后来也开源了出去。市场反应其实挺正向。

**Colin**：**与此同时**，我们跟 **T-Mobile** 也启动了合作——他们的体量是 Klarna 的 **10 倍级**（政策数量、复杂度、调用量都翻 10 倍）。我们发现这套框架在 T-Mobile 跑起来也还行，只做了少量扩展。

**Colin**：于是我们拉上产品团队说："看，我们有在生产里跑的客户，这些原语是 work 的，Swarm 在 GitHub 上拿了不少 star，内部影响也大。"**最后我们和产品团队一起，建了一个专门团队，把它做成 Agent SDK**。

**主持人**：最近你们还发了 **Agent Kit**？

**Colin**：对，Agent Kit 是可视化的搭建器——但**它是这个故事的延续**：

- 第一步：找到**参数化指令和工具**的方法；
- 第二步：做出**框架**，让推广变简单；
- 第三步：用 **Agent Kit** 让框架更容易被采用。

**Colin**：整条线**起点是 2023 年 Klarna 的一次解决方案架构师交付**——但完全是 FDE 式的交付。**今天，FDE 团队全员把 Agent SDK 当成工具箱里的标配**。

**主持人**：太神奇了。从 Klarna 起步，到 Swarm，到 Agent SDK，到 Agent Kit。**一个真正由 FDE 团队打造、在外流通的产品**。

**Colin**：对。我前老板 Shoa Sunkar 在 Palantir 时说："FDE 的工作就是吃痛，排泄出产品。"——**看来我们确实排泄出产品了**。

**Colin**：（笑）**完全正确**。

## 9 客户合作的"前后对比"

**主持人**：吃痛之外，给我们讲讲**客户前后发生了什么变化**。如果我是有幸跟你们合作的企业客户，FDE 来之前和走之后，我会有什么不同？

**Colin**：变化分两块：

1. **你解决的问题**——通常有一个**可量化的 ROI**。你会多出一块原本不存在的软件，专门解决你那个特定问题；
2. **你掌握的工作方式**——不只是软件本身，你还会掌握 FDE 那种 LLM 开发的方法论。

### 9.1 交付物：软件 + 工作方式

**Colin**：我们一般会**和客户那边一组工程师搭档交付**，或者**和合作伙伴一起做**——他们会接手后续运营。**我们把自己定位成 0 到 1 团队**——进场，把困难新颖的问题"打掉"，然后**转去下一个问题**，不想长期驻场。

**Colin**：除了软件和 ROI 之外，还有一份资产是**FDE 的工作方式**。客户学到的应该是：

- **编排**端到端工作流；
- **用评测**把它包起来；
- **用护栏**保护运行时那些你控制不住的边界；
- **反复建评测集**，**测试应用的一致性**；
- **学会如何做出可以信任的应用**。

**Colin**：我们希望一旦我们解决完最初的问题，**你不再需要 FDE 回来**。当然在实践中——比如半导体那个项目——这些"积木"自己就开始变成独立的应用，我们可能就继续往上搭了。

**主持人**：但**首选的模式**是：**找到难题 → 解决 → 抽取经验 → 转到下一个客户**。

**Colin**：对。

## 10 IVACO 现场演示：关税场景下的供应链智能体

**主持人**：有没有什么**你们留下的产品**可以现场展示给我们看？

**Colin**：有的。我这里正好有一个——是给一家制造业客户做的。我打开给你看。

**主持人**：没什么比现场演示更好了。给我们讲讲。

**Colin**：我先解释一下你在看什么。这是给一家叫 **IVACO** 的客户做的——他们在汽车行业。这是个**简化版**，他们的真实问题：他们有极其复杂的供应链，**任何一个会影响零部件供应的事件**——都需要在多个团队之间沟通协调：制造部、物流部，再到真正组装零件的工厂。

**主持人**：那他们原来怎么做？

**Colin**：**原来全靠人打电话**互相沟通。我们做的事是：

- **第一步：搭数据层**——我们不动数据本身，只是做了几个 API；
- **第二步：把 LLM 塞进去当编排器**——LLM 查询这些数据，**直接给出原本要花几小时甚至几天才能拿到的初步洞察**。

### 10.1 演示：25% 关税冲击

**Colin**：好。**演示场景**：我们有个客户刚听说**"中国到韩国加征 25% 关税"**。**正常情况下**，这需要跨团队协调——找出哪些零件受影响、影响供应链的哪一段、然后跑一堆仿真，找最合适的绕路方案。

**Colin**：我们这次用 LLM 来处理。**问题在于**：变量太多，而 LLM 是概率性技术——如果你给它完全的自由度，**你不会信它的结果**。所以我们同时搭了**决定性护栏**——模型出来的方案，**永远可以用决定性方法验证**数字是否对得上，然后再去做真正的业务决策。

### 10.2 决定性约束：100% 确定的部分不交给模型

**Colin**：我们为客户搭的"关卡"长这样：不管模型给什么供应链方案，**都得过一组决定性约束**：

- **轮胎至少要 2 家供应商**——避免单一来源卡死；
- **不能超 lead time**；
- **不管换哪家供应商，材料必须全数覆盖**。

**Colin**：这些是你想**100% 强制**的——**不交给 LLM 做，用决定性逻辑写死**。这是 FDE 团队做事的一个**一贯原则**：**只要能决定性地做，就决定性地做；把 LLM 留给它们最擅长的部分**——也就是那些**需要细微判断**的概率性工作。

### 10.3 演示运行

**Colin**：好，我们来跑这个场景。我先输入：*"中国到韩国 25% 关税的影响"*。**这里有几个控件我们一开始就搭进去了**——因为客户偏保守，不大信 LLM。

**Colin**：我们做的第一件事是**让模型先解释它的推理过程**——这是基础控制，但我们把所有这些层面都摆给你看。我们还提供一堆**可视化小部件**——让结果能直接被看清楚，比如这里显示"关税"、"对不同零件的影响"。

**Colin**：如果用户**还是不信**，我们还提供**决定性校验**——比如展开这个明细表，可以核对模型用的关税值对不对。看这里——所有原产中国的零件都按我指定的关税百分比被打上了。

**主持人**：地图上也能看出来——关税**精确命中**了对应的工厂。

**Colin**：对。第一步就是这个——**商业智能**。以前要 BI 团队写一堆 SQL 才能拿到的信息，现在模型直接做出来，**等于把数据访问权民主化了**。

**Colin**：**真正有价值的部分**是第二步——要跑复杂的仿真：找一组工厂组合，**同时最小化 lead time 和成本**，权衡各种 trade-off。这种事你**不想直接问 LLM**——但我们可以**把模拟器给 LLM 用**。

**Colin**：模型可以**用商业用户会调的那些参数**做调整，然后跑一堆仿真，挑出最好的那个。这个例子里我们跑**5 次优化**——实际生产中，这正是最近大家用 Agent 方式做得很成功的地方：**让 Agent 在离线状态跑成百上千次仿真**，然后带着"为什么这是对的 trade-off"的文档化方案回来。

**Colin**：跑完之后，会回这样一张表——**5 次运行的 trade-off**，**挑最优的那次**。模型给建议，我们接受，**"plan is final"**。

**主持人**：跑完了。看，新的方案回来了——

- **通过了我们的决定性校验**——我们安心；
- **关税应用正确**——我们可以确认；
- **地图上也对得上**——这次用了**台湾的工厂**，而以前很多零件来自中国。

**Colin**：这就是一个**快速演示**——我们把细节简化了，但下面**每一层都是我们在制造业和其他行业真做出来的东西**。

## 12 给 AI 时代创业者的建议

**主持人**：FDE 人才稀缺，很多创始人和 CEO 来找你——他们想搞 FDE 模式，想了解**经济学、怎么挑客户、往哪部署 FDE**。你有什么建议？

**Colin**：第一件事是**先想清楚你的 FDE 团队要达成什么**：

- 你要**靠服务收入当主要营收**吗？
- 还是**赌产品押注**？

**Colin**：这两种是**完全不同的运动**。我们押的是后者——赌 FDE 交付里能冒出成功产品，**带来营收增量**。

### 12.1 警惕"服务收入陷阱"

**Colin**：**最关键的事**：很多人想两条腿走路，**但结果往往两边都做不好**。我以前在咨询行业看过太多这种失败模式：

- 公司的愿景是"我们最终要做成产品公司"；
- 但**服务收入的短期诱惑**会慢慢把所有人和资源都拖进去；
- 最后**战略视角彻底丢失**。

**Colin**：OpenAI 之所以"幸运"，是因为我们骨子里**是研究公司，后来变成产品公司**——这两种身份让我们能战略性地排优先级。

**主持人**：那你的建议具体是什么？

**Colin**：

1. **想清楚 FDE 的目的**；
2. **全力推到底**；
3. **准备好在最艰难的时刻说"不"**——哪怕客户要给你很多钱做不战略的事；
4. **守住底线**：**最后必须交付一个产品或平台**。

### 12.2 OpenAI 的双轨策略

**Colin**：但我得破一下自己的规矩——其实**有两条线**：

- **有时是非常有经济价值的问题**，我们不确定能不能沉淀成平台——但**问题本身太有价值**，我们相信"**如果模型能更好解决这类问题**，对 OpenAI 也是 net good"——这种客户我们也排进去；
- **有时是有明确产品假设的**——我们找**完美的设计伙伴**去建客服应用、临床试验文档写作方案等。

**Colin**：**团队的能力是按这两条线分**的。一边是**行业**——半导体、生命科学——我们找有"大问题"的合作伙伴；另一边是**具体产品方向**——找"完美的设计伙伴"。

## 13 FDE 会发通用产品吗

**主持人**：那追问一句——你们在为客户做产品的同时，**OpenAI 会把这些产品发给那些 FDE 团队没介入的长尾客户吗**？我们该期待 OpenAI 出一款客服产品，或生命科学、半导体产品吗？

**Colin**：不能讲太多细节。**这件事对我们是开放的**——我们在看**额外的商业化路径**。但有一点我能说：

**Colin**：**FDE 是 0 到 1 团队**。**产品端**的路径是这样：

1. **先证明一个产品假设**；
2. **再做 2-3 次**——让复用度从 20% 涨到 50%；
3. **再推向规模化业务**——在市场里反复做。

**Colin**：**这是我们想要建立的动作**，但坦率讲我们**还在非常早期的阶段**。我们有一堆假设，还在赌该往哪边下注。

**主持人**：研究型押注那边呢？

**Colin**：**研究型押注**——解决大行业问题——**我们不太可能去做一个"垂直行业产品"由 FDE 团队去支持**。但我们**希望**——通过解决这些高价值问题，**一个有用的横向平台能自然涌现出来**。我们对这条路径也开放。

**Colin**：**真正的押注更多在产品这一侧**。

**主持人**：所以 0 到 1 → 50%、60% 复用 → 推向市场。

**Colin**：对。

## 14 失败经验：过早泛化是最大错误

**主持人**：换个角度——**"不要做的事"**。你肯定见过很多最终没沉淀出产品、也没沉淀出学习的项目。**这些案例有什么共同点**？

**Colin**：**我们确实踩过一堆坑**。但**最大的一个错误是"过早泛化"**。

**主持人**：怎么讲？

**Colin**：在 OpenAI 有些时候——因为我们有 ChatGPT——会看到 ChatGPT 的某个功能，心想："**这对企业来说肯定是个绝佳的通用方案**。" 然后**我们倒着去找问题**。

**Colin**：结果发现**很多时候跑不通**——因为**我们没做 0 到 1**，只是**部署一个泛化方案**，根本不管用。

### 14.1 LLM 圈的高概念陷阱

**Colin**：我感觉**整个 LLM 圈**有**太多"高概念方案"**——**没有明确解决的问题**。反过来说，**每当我们真的把客户问题扎得很深、说"我们就要解决这个具体问题"**——**几乎每次都自然沉淀出可复用的东西**。

**Colin**：所以**过早泛化**是我们踩过的最大坑，**也是学到的最重要的一课**。

**主持人**：我记得 Paul Graham 说过："**不要担心过早考虑规模化，先解决一个具体问题**。"

**Colin**：**"做不 scalable 的事"**——这是我们团队的口号之一，**我们就是这么干活的**。

## 15 快问快答：看多 / 看空 / 被低估

**主持人**：来一组快问快答。我最喜欢这个。**"看多-看空"游戏**——你做过的最爱玩的。**挑一个被低估、即将大爆发的想法/公司/业务**；再挑一个**名头响、但实际"虚火"的方向**。

### 15.1 看多：元数据翻译层公司

**Colin**：有意思。先讲**看多**的——**我看 FDE 把项目带到生产**花的时间，绝大部分都卡在**一件事**：**在原始数据之上，搭一层"翻译层"**，把业务逻辑注入进去，**让 LLM 能真正用上这些数据**。

**主持人**：那不就是 MCP 加连接器吗？

**Colin**：很多人起步就是 MCP、加连接器——但**我们反复做的一件事**是**在中间搭一层"轻量逻辑层"**——**模型用它来取数**。比如："什么时候该把数据仓库的内容和 SharePoint 里的内容混起来，回答一个复杂问题？"

**Colin**：**做这类事的公司**——**可以叫"元数据翻译层"**——**我相当看多**。

**Colin**：有意思的是，**这其实是个老概念**——你看 Collibra 这类工具，做的就是**元数据文档化**。但**现在 LLM 能用上这些元数据了**，**这事的价值就起来了**。**问题本身不是新的**——经典的两难："是把数据搬到一个好用的地方，还是在原地建一层？"

**Colin**：**没变的就是这个问题**。**变了的是**——以前要人写查询，**现在 LLM 替你写**。要不要搬数据？这些事**我们没最终答案**，但这是个**非常有意思的空间**——**能省下大量 FDE 部署时间**，**也能把数据访问权民主化**。

### 15.2 看空：只做单环节的 LLM 工具

**Colin**：**看空的方向**——先说我有偏见——**我主要和企业客户打交道**。如果你看 **LLM 应用上生产的完整链路**：

1. 编排工作流；
2. 加 tracing；
3. 标注数据；
4. 搭评测；
5. 上护栏。

**Colin**：**只做这条链上某一环的公司**——**企业里就是吃不开**。原因：**光把一个 LLM 应用带上生产就已经够难了**——就算所有工具都是同一套。**再加上把所有工具拼起来的集成问题**——**对很多企业是"再压一根稻草"**。他们**想要一个"一站式"合作伙伴**。

### 15.3 被低估：OpenAI Playground

**Colin**：**被低估**——**不低估的那个**：Codex，**第一次打开它**，我去开了 4 小时会，**回来发现事情已经做完了**——"这是魔法"。

**Colin**：**被低估的那个是 Playground**。**就是 platform.openai.com 上的 Playground**。它简单到——你贴个截图进去，**直接和 API 交互**。

**Colin**：**我用它做的演示数不清**——**它能非常快速地回答"这个用例到底行不行"**。我举一个例子：我在判断一个**浏览器自动化用例**到底能不能做。我截了一张网页图，丢进 Playground，开始测——"**10 次里能不能中 7-8 次**？能的话，生产里就大概率能跑。"

**主持人**：**这正是我玩出我的"啊哈时刻"的地方**——在 ChatGPT 之前——我在玩 **Da Vinci 003**。我就在 Playground 上跟它聊，我说"哇哦"。后来 ChatGPT 出来了，我心想："**我早说过了**。"

**Colin**：哈哈对。**Playground 是个被严重低估的工具**。
