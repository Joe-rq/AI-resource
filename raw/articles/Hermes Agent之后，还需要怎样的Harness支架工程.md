Hermes Agent 之后：AI 开发需要一层治理协议
=============================

wow-harness v3 技术分享

Hermes Agent 登上 OpenRouter 全球日活第一。Superpowers 进入 Anthropic 官方插件市场，半年 196,000 Stars。Claude Code 被学者逆向分析成论文发表。OpenHands 在 SWE-bench 跑到 77.6%。

这四个工具分别把 AI 开发的四个环节做到了工程可用：Claude Code 让 AI 写代码的质量足够好，Superpowers 让 AI 按纪律做事不偷懒，Hermes 让 AI 记住你的偏好越用越懂你，OpenHands 让 AI 在沙箱里安全执行。

但你跟任何一个用了这些工具超过两个月的工程师聊，他们大概率会说同一件事：

**AI 写得越多，我维护它越累。**

不是 AI 不够聪明。是它每次都在重新发明你之前已经建立过的约定。

这篇文章介绍 wow-harness v3——一个面向这个问题的治理协议设计。我们先看清楚现有工具为什么没碰这件事，再展开 v3 具体怎么解决，最后看这个方向在学术界的独立验证。

一、为什么现有工具都没碰这件事
---------------

四个工具有一个共同特征：**都在优化 "一个人 + 一个 agent" 的体验**。

Claude Code 让这次 session 写出来的代码更好。Superpowers 让这次 feature 的流程更规范。Hermes 让下次 session 还记得上次。OpenHands 让这次执行更安全。

但一个真实项目不是跑一次。它跑几十次、几百次。不同的 session、不同的 agent、不同的阶段——它们之间怎么保持一致？

具体说：

你跟 AI 工作了两周，建立了一些约定——API 字段叫什么、错误码什么含义、模块之间谁负责什么。这些约定没有存在任何正式的地方。第三周换 session，AI 不知道这些约定，根据模型常识猜了一个不同版本。八周后，你的系统里有好几套互相矛盾的设计思路，每套都是 "某次 session 当时觉得最合理" 的产物。

过去这件事靠人管。但 AI 产出代码的速度已经超过人脑能跟上的速度了。

Anthropic 自己在 Claude Code 的大型代码库部署博客里写了一句很关键的话：**"真正决定效果的，是围绕模型搭起来的那套'套具'（harness），对最终效果的影响远超模型本身。"** 一篇对 Claude Code 源码的学术逆向分析（arxiv 2604.14228）也印证了这一点：整个 Claude Code 代码库中 98.4% 是运行基础设施，只有 1.6% 是 AI 决策逻辑。

套具比模型重要——但目前的套具都在管 "一次做好"。管 "一百次之间不漂移" 的套具，还没有人做。

二、wow-harness v3 怎么解决
---------------------

v3 的设计不是围绕 "AI 怎么写代码"，而是围绕五个具体问题。每个问题都来自真实开发中反复出现的失败。

### 问题 1：AI 做过的事，怎么不丢？

**场景：**三个月前 AI 做了一个架构决策，当时的推理过程在对话窗口里，session 关了就没了。三个月后另一个 agent 碰到同样的问题，不知道之前怎么决定的，又做了一个不同的决策。

**v3 的做法：**所有 agent 的产出——每一次代码改动、每一个判断、每一次概念的调整——都作为事件写入一条只追加、不可篡改的时间线。这条时间线是整个系统的唯一真相来源。三个月后的 agent 不需要 "记得"——它查时间线就能看到完整的决策历史，包括是谁做的、什么时候、为什么。

但时间线会越来越长。跑了半年，事件量可能很大。所以 v3 同时设计了两个配套机制：一个负责从时间线增量推导 "当前状态"（不需要每次从头扫），另一个负责定期把历史归并压缩成关键快照（保留可追溯性但减少存储负担）。

### 问题 2：工程概念跨 session 怎么不漂移？

**场景：**第一周约定了一个 API 叫 getUserProfile，返回 5 个字段。第三周另一个 agent 觉得应该返回 8 个字段还改了名字叫 fetchUserData。第五周又一个 agent 不知道改过名，又按老名字写了调用。

**v3 的做法：**每个工程概念（API 定义、数据结构、命名约定、架构决策）在系统中是一个独立的节点，有自己的生命周期：创建 → 修改 → 被替换 → 退役。概念被替换时，系统自动扫描 "谁还在用旧版本" 并通知——不靠 AI"记得"，靠结构自动传播。

而且，替换操作有一个关键约束：**必须说明引入了什么之前没有的新信息**。如果说不出来——比如只是 "我觉得新名字更好"——系统不允许替换。这一个机制就解决了长期项目中很常见的振荡问题：同一个设计在两个版本之间来回改，每次改回去的 agent 都不知道之前为什么改走。

### 问题 3：怎么确保 AI 的产出真的做完了？

**场景：**AI 说 "修完了"。你看了看，代码确实改了，但它改了主文件却没同步测试文件。或者它改了 API 返回值却没更新文档。更常见的是——它自己觉得修完了，但实际上原来的 bug 换了个位置又出来了。

**v3 的做法：**分两层验证。

第一层，agent 自己在提交前必须跑一组自检项，每一项要有具体的验证证据（命令输出、测试报告、grep 结果），不是 "我觉得做完了" 的主观声明。这组自检项通过一个统一的提交检查点——**物理层面**拦截不合格的产出（不是 prompt 层面 "建议你做自检"）。

第二层，另一个独立的 agent 对同一份产出做交叉验证——用不同的视角、不同的方法。验证 agent 的工具列表里**没有写权限**（schema 级限制，不是提示词约束），保证它只能看不能改——做判断的人不能同时是做事的人。

这跟 Superpowers 的 "强制 TDD" 有本质区别。Superpowers 在提示词层面要求 Claude 遵守纪律——Claude 理论上可以 "合理化" 自己不遵守。v3 的检查点是物理拦截：自检不过就提交不了，不存在 "我觉得差不多就行了"。

### 问题 4：怎么让 AI 不是 "一个工具" 而是 "一个自己运转的组织"？

这是 v3 跟所有现有工具差异最根本的地方。

Superpowers 的设计假设是：agent 是一个需要被管教的执行者——你告诉它 "先写测试再写代码"，它照做。下一个任务再告诉它一遍。每次都是人给指令、agent 执行、session 结束。

v3 的设计假设完全不同：**agent 不是执行者，是组织成员。多个 agent 组成一个自己运转的开发组织——有采访员、有架构师、有执行者、有审查员、有修复师——它们之间的协作不靠人调度，靠协议自动驱动。**

具体怎么做到：v3 的核心结构是一张**自动扩张的图**。每个节点是一个 agent skill（采访、设计、规划、执行、审查、修复），边是事件触发关系。当一个节点完成工作产出事件，系统自动检查 "这个事件应该触发哪个下游节点"——然后自动 spawn 一个新的 agent session 去跑那个节点。

举例：执行 agent 写完代码 → 产出 "任务完成" 事件 → 系统自动 spawn 审查 agent → 审查发现问题产出 "发现缺陷" 事件 → 系统自动 spawn 修复 agent → 修复完成产出 "修复完成" 事件 → 系统自动 spawn 审查 agent 做闭合验证。**整条链路没有任何人参与调度**——图自己在扩张、收缩、运转。

而且每个新 spawn 的 agent session 都是 "无状态" 的——它不继承上一个 session 的偏见和惯性。它拿到的是系统专门为它组装的上下文胶囊（包含它需要知道的概念、约束、引用关系），从 artifact（代码、测试、合约）出发做独立判断。这就像一个新员工入职——他不需要 "记得" 前任怎么想，他看交接文档就能开始工作。

这意味着什么？**项目负责人说完需求就可以退场。后面的一切——设计、规划、执行、审查、修复、集成——是 AI 组织自己完成的。**项目负责人想看进度随时能看，想叫停随时能停，但正常情况下不参与。

这跟 Superpowers "brainstorm → plan → TDD → review → finish" 的线性流程有根本区别。Superpowers 是一条直线——人启动、agent 走完、人验收。v3 是一张图——图自己根据事件流决定下一步该做什么、该 spawn 谁、该通知谁。直线做不了并行（5 个 agent 同时做 5 个任务），做不了回路（审查发现问题 → 自动触发修复 → 修复完自动触发闭合验证），做不了跨任务的概念冲突检测。图可以。

### 问题 5：项目负责人怎么不退化判断权？

**场景：**AI 越来越自动化，项目负责人发现自己要么被拉进了大量工程细节（"这个分支要不要合并？这个测试要不要跑？"），要么完全退出了判断循环（AI 自己做了所有决定，事后才发现方向偏了）。

**v3 的做法：**严格区分两类决策。

工程实施类决策（怎么写、怎么测、怎么部署）——AI 自己做，不问人。系统所有者的时间不应该花在这些事上。

语义判断类决策（产品方向、不可逆操作、价值取向）——必须走 "升级" 路径送到系统所有者面前。关键是怎么送：不用工程黑话，用产品语言描述情况、列出选项和各自代价，让系统所有者直接判断 "要 A 还是 B"。

系统所有者的每次判断本身也是一个事件，写入时间线、永久留痕。这意味着 "人做了什么决定、什么时候、为什么" 跟 "AI 做了什么" 一样可追溯。

三、这个方向的学术验证
-----------

2026 年 2 月，一篇叫 ESAA（Event Sourcing for Autonomous Agents，面向自主 Agent 的事件溯源）的论文出现在 arxiv。它的核心命题跟 v3 的设计高度重合：

> 论文提出**把 agent 的 "想做什么" 跟 "系统实际发生了什么" 分离**——agent 只发出结构化的意图声明，由一个独立的验证器检查后才写入不可篡改的事件日志。这跟 v3 中 "事件意图 → 提交检查点验证 → 事件记录" 是同一个架构。

> 论文指出 **AI 开发正在从 "对话式" 转向需要 "长期一致性" 的工作流**——在几十个周期和产出物之间保持连贯。这正是 v3 的概念图 + 演化链 + 新颖性检查要解决的核心问题。

> 论文描述了一种叫 "状态漂移" 的失败模式——**agent 相信自己修复了问题，但系统实际并没有变**。这是 v3 的双层验证 + 物理拦截要消除的失败。

ESAA 目前是论文阶段。v3 的工程设计在多个维度上超出了论文范围：概念节点的生命周期状态机、约束规则（义务）的独立生命周期管理、为每个 agent session 精确组装上下文的机制、基于证伪主义的三正交审查方法论、闭合合约驱动的缺陷修复协议。这些论文都未涉及。

ESAA 的出现是个好消息——意味着这个方向不是孤立的判断，而是领域的必然趋势。

四、跟现有工具的根本区别
------------

这不是 "我们跟他们分别在不同层" 这么温和的关系。设计理念上有根本分歧。

**Claude Code 是 v3 的地基，不是竞争对象。**v3 跑在 Claude Code 上面——用它的终端环境、它的子 agent 机制、它的工具系统。Claude Code 管的是 "单次 session 怎么高效执行"，v3 在这个基础上加了 "跨 session 的组织级治理"。两者不是同一层的问题，不存在替代关系。

**真正在同一层竞争的是 Superpowers、Hermes Agent 和 OpenHands**——它们各自试图解决 "AI 怎么变得更有用"，但设计假设跟 v3 有根本分歧：

**Superpowers 把 agent 当需要管教的执行者。**它的 14 个 skill 文件本质是行为约束清单——"你必须先写测试"、"你不能跳过 review"、"你必须分步骤规划"。每条规则都预设 agent 会偷懒、会走捷径、需要被提示词强制约束。而且每次 session 重新加载一遍——因为 agent 没有跨 session 的状态。

v3 不需要这些约束。v3 的 agent 拿到的不是 "你应该怎么做" 的行为清单，而是**一个完整的系统理解**——它知道自己在整个组织里的角色、知道上下游是谁、知道当前概念的状态和引用关系、知道什么约束生效。它的行为不是被清单约束出来的——是从系统理解里自然推导出来的。这是 v3 的一个核心设计原则：**"解释为什么" 比 "堆 MUST 规则" 有效得多**。当 agent 理解了系统的运作方式，它自然知道该怎么做；当它只有一份规则清单，它只知道不该做什么。

**Hermes Agent 是一个人的助手。**它的整个架构围绕 "一个用户 + 一个 agent" 设计——记住你的偏好、学习你的工作模式、在你的消息平台上等你。它没有 "多个 agent 之间怎么协作" 这个概念，因为它的设计假设里只有一个 agent。

v3 从第一天就假设多个 agent 并行——不是一个 agent 变聪明，是一群 agent 变成一个组织。这是完全不同的工程挑战。

**OpenHands 的事件流是临时的。**OpenHands 内部有 EventStream 架构，但这是 session 内部的消息总线——用来在 agent、模型、运行时之间传递消息。Session 结束，事件流消失。v3 的事件时间线是永久的——它不是消息传递工具，是系统的历史记录和真相来源。两者看起来名字像，工程含义完全不同。
