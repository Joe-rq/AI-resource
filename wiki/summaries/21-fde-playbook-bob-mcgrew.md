> 前 Palantir 早期高管、前 OpenAI 研究主管 Bob McGrew 深度解读前置部署工程师（Forward Deployed Engineer）模式的起源、运作方式，以及为何在 AI 创业时代全面复兴。

## FDE 定义：填补产品与客户之间的鸿沟

**Forward Deployed Engineer（前置部署工程师）** 是一个技术背景的工程师，驻场在客户那里，填补"产品实际能做的"和"客户实际需要的"之间的鸿沟。FDE 交付的不是软件功能，而是**结果（Outcome）**——拿着已有产品，在产品团队配合下，琢磨怎么把这个结果真正交付给客户。

## Palantir 起源故事：从为间谍做软件到平台模式

Palantir 创业时的目标是**为情报界造软件**。由于不认识间谍、间谍也不会告诉你他们做什么，团队只能先做一个 Demo，带去给潜在客户看。创始人 Stephen Cohen 的做法是：演示原型，客户说"这个太烂了"，他就记下所有反馈回去改。

但真正催生 FDE 战略的关键转折是：**每个客户需要的产品都有点不一样**。如果为每个客户做定制功能，就做不下去了。于是 Palantir 转向**平台（platform）而非产品**的思路——建一个有大量可定制能力的平台，派人到现场理解用户、构建定制。

> 如果你的生意能直接规模化、对所有客户一视同仁地对待，那你已经被赐予了一份大礼——别碰 FDE 战略。但这条路对我们不灵。

## Echo 团队与 Delta 团队

FDE 模式有两个核心角色：

- **Echo 团队（嵌入式分析师）**：去客户现场，搞清楚什么 Demo、什么用例对这个站点真正有意义。同时也是客户经理。经典画像是领域内的"老兵"，但必须是 **"异端（heretics）"**——懂得现状、同时承认现状不够、必须推倒重来。
- **Delta 团队（部署工程师）**：实质上是软件工程师，极其擅长快速写代码、吞下大量痛苦。要找的不是"工匠型"工程师（喜欢完美抽象、构建可维护十几年的软件），而是**能冲进去、写粗糙但能用的代码、在时间线内交付结果**的人。

## 碎石路与柏油路

这是 FDE 模式最核心的隐喻：

- **FDE 铺碎石路（gravel road）**：把产品接到客户实际需要的地方，只解决一个非常具体的问题，用最简单的方法。
- **产品团队铺柏油路（paved superhighway）**：看着碎石路，想清楚怎么把它推广到接下来 5 个、10 个客户，铺成柏油超级高速公路。

这里有一个经典失败模式：FDE 给一个客户实现了功能，产品团队直接把它带进产品——结果是**对单个客户过度定制**。正确的做法是猜出"你真正在解决的问题"，它永远比客户嘴上提出来的更普适。Palantir **本体论（Ontology）** 的诞生就是典型案例：把具体对象类型抽象为"对象、属性、链接"的通用概念，让客户自己定义类型。

跨客户共创是消解"通用化 vs 专门化"张力的关键方法：**把 3 个不同客户的 FDE 同时请进来共同设计产品**，让所有人看到三种工作流的微妙差异。

## FDE 与 PMF 的核心 KPI 差异

这是两种战略的根本分野：

- **PMF 战略**：希望为每个客户做的工作**越来越少**，把成本打下来，合同规模保持不变。
- **FDE 战略**：希望把**合同规模做上去**，每个客户身上的定制量可以保持不变——因为你做的是越来越有价值的工作。

> 内部指标是**合同规模**，不一定是你为每个客户做的客户工作量。

此外，**产品杠杆率（Product Leverage）** 是另一个关键指标：FDE 能不能用你的产品向客户交付更多价值，而**不需要再额外拉三个工程师过来**？如果抽象做得好，FDE 会主动选择使用你的产品，而不是自己搞一次性方案——形成内部市场动态。

## 为什么 AI Agent 时代 FDE 全面复兴

三年前 YC 招聘板上 FDE 岗位基本为零，现在超过 100 家 YC 系公司在招。核心原因：

1. **AI Agent 是全新品类，没有成熟产品可替代**。标准 SaaS 是"用一种付款方式取代另一种付款方式"，市场定义清晰，不需要大量产品发现。AI Agent 完全不同——有大量产品发现要做，而那些发现**只能从企业内部做出来**。
2. **市场有惊人的异质性**。不同行业、不同客户的 AI Agent 需求差异巨大，就像反扩散工作流和反恐工作流的工作方式截然不同。
3. **合同规模足够大**。高接触、大量定制的工作方式在经济上可持续，不像传统 SaaS 初创公司那样必须尽快停止手把手的流程。

> AI Agent 领域没有成熟产品可替代。可能五年后我们回头看，会说"AI Agent 当时根本不是个东西，我们其实是在做一堆不同的事"。

## Demo 驱动开发

FDE 模式天然要求反复给新客户做 Demo。这改变了工程师的思维焦点：从"我能造什么"变成"客户想要什么、我在解决客户的痛点吗"。好的 Demo 让客户产生**渴望（desire）**——他们想伸手去抓住它、把它带进自己的生活。

> Demo 驱动开发迫使你开发出更好的产品——因为你不只是在想每个功能独立看是否合理，而是"我要一遍遍展示这个 Demo，这些功能要怎么协同工作"。

## 学习型组织：FDE 模式的终极底色

FDE 模式要求构建的是**学习型公司（learning company）**。大公司可以靠同一个战略继续滑行，但 FDE 驱动的组织必须永远在打磨、永远在学习。这也是为什么 Palantir 走出了数量惊人的创业者——**这正是在每个客户站点上做创业者的训练**，但你可以调用强大的产品杠杆。

## 与 Agent 基础设施的关系

FDE 方法论与 Agent 平台开发存在类比层面的关联，而非直接技术重叠：

- **[[Thin Harness, Fat Skills]]**：FDE 的"碎石路→柏油路→高速公路"飞轮与 skill 生态演化路径有结构相似性。FDE 在客户现场定制的解决方案相当于 fat skills，平台提供的通用能力相当于 thin harness。但 FDE 飞轮描述的是人类组织的产品化过程，skill 生态描述的是代码模块的复用机制——两者在"定制→抽象→平台化"的抽象模式上一致，具体运作机制不同。
- **[[Agent Macro Evaluation]]**：FDE 的 TTFV（Time to First Value）指标为 Agent 部署效果评估提供了可借鉴的思路——从部署到价值实现的时间同样是衡量 Agent 系统实际效用的关键维度。但 Expansion Rate 和 Productization Rate 是组织级指标，在 Agent 系统评估中缺乏直接对应物。
- **[[Claude Code Skills|Claude Code Skills]]**：FDE 的"教会客户自己使用，最终让自己变得不必要"与 skill 的自服务设计理念一致——好的 skill 应降低对开发者的依赖。这是 FDE 方法论中与 Agent 平台实践最直接的连接点。

总体评估：FDE 飞轮与 skill 生态演化之间存在有价值的类比关系，但 Bob McGrew 的实战手册本身是纯 FDE 方法论，不直接涉及 Agent 基础设施技术。
